# T005.1: UI de perfiles SAT y e.firma

## Estado

Pendiente

## Prioridad y tamano

- Prioridad: Alta.
- Tamano: Mediana.

## Objetivo

Permitir crear y editar perfiles SAT desde la UI, registrar su e.firma mediante `SecretStore` y mostrar si el perfil esta listo para crear solicitudes.

## Contexto

El MVP requiere un perfil SAT antes de crear solicitudes. La pantalla debe conectar la persistencia de `T003` con el almacenamiento seguro de `T005`, sin exponer secretos a QML ni a SQLite.

## Alcance

### Incluye

- Pantalla de perfiles SAT.
- Alta y edicion de RFC y datos descriptivos del perfil.
- Seleccion de archivos `.cer` y `.key`.
- Captura de contrasena de e.firma.
- Invocacion del caso de uso de registro de e.firma.
- Indicador de credencial valida y perfil listo/no listo.
- Mensajes visibles para validaciones y errores de Keychain.
- Reemplazo de e.firma desde la UI.

### No incluye

- Consulta SAT real.
- Creacion de solicitudes.
- Administracion de usuarios, clientes o roles.
- Exportacion o migracion de credenciales.
- CSD para timbrado.

## Dependencias

- `T002-shell-qt-qml.md`.
- `T003-persistencia-local.md`.
- `T005-secret-store-keychain.md`.
- `docs/requirements.md` RF-001 y RF-002.

## Trabajo esperado

1. Crear `PerfilesSatPage.qml` y su view model C++.
2. Implementar formulario de alta y edicion de perfil.
3. Conectar seleccion de `.cer`, `.key` y captura de contrasena con el caso de uso de perfiles.
4. Conectar el caso de uso con `SecretStore` y el repositorio de perfiles.
5. Mostrar estado listo/no listo sin revelar el motivo sensible completo.
6. Permitir reemplazar la credencial activa solo despues de validar la nueva.
7. Impedir guardar perfiles activos con RFC duplicado.
8. Agregar tests de view model y casos de error usando fakes.

## Restricciones tecnicas

- QML no lee, copia ni almacena directamente la llave privada o la contrasena.
- La UI no decide si certificado y llave corresponden; recibe el resultado del caso de uso.
- La contrasena debe limpiarse despues de entregarla al caso de uso cuando sea posible.
- Los mensajes no deben mostrar rutas sensibles, contenido de certificados ni secretos.
- Un perfil no esta listo para solicitudes hasta que `SecretStore` confirme todas las validaciones.

## Criterios de aceptacion

- [ ] Se puede crear un perfil con RFC y datos descriptivos.
- [ ] No se puede guardar un RFC duplicado entre perfiles activos.
- [ ] Se pueden seleccionar `.cer` y `.key` desde la UI.
- [ ] La contrasena se entrega al caso de uso sin persistirse en QML o SQLite.
- [ ] Una e.firma valida deja el perfil marcado como listo para crear solicitudes.
- [ ] Una contrasena incorrecta muestra un error y no activa la credencial.
- [ ] Un certificado o llave incompatibles muestran un error y no activan la credencial.
- [ ] Un RFC de certificado distinto al perfil muestra un error.
- [ ] Una e.firma vencida o invalida muestra un error.
- [ ] Reemplazar una credencial valida conserva una sola credencial activa.
- [ ] Si el reemplazo falla, la credencial anterior continua utilizable.
- [ ] El perfil no expone secretos en pantalla, SQLite o logs.
- [ ] El formulario funciona con un `FakeSecretStore` en pruebas.
- [ ] El usuario puede volver a la lista de solicitudes sin crear una solicitud SAT.

## Verificacion

1. Crear un perfil valido usando `FakeSecretStore`.
2. Probar RFC duplicado.
3. Probar e.firma valida, contrasena incorrecta, pares incompatibles, RFC distinto y certificado vencido.
4. Probar reemplazo exitoso y fallido.
5. Inspeccionar QML, SQLite y logs para confirmar ausencia de secretos.
6. Ejecutar `ctest --test-dir build`.

## Definicion de terminado

- La pantalla permite administrar perfiles SAT sin acceso directo a secretos.
- El perfil muestra correctamente si esta listo para crear solicitudes.
- El registro y reemplazo de e.firma usan `SecretStore`.
- Los errores principales tienen mensajes visibles y no filtran informacion sensible.
- `T009` puede asumir que un perfil marcado como listo tiene una credencial valida.
