# T025.5: Restauracion transaccional

## Estado

Completada (2026-10-22); comprobacion manual trasladada a T025.6.

## Objetivo

Restaurar un respaldo: verificacion completa en staging, migracion de esquema, borrado de credenciales, marcador durable, relanzamiento y sustitucion al arrancar con `pre-restauracion-<fecha>`.

## Contexto

Epica T025, decisiones D1 a D19. Ver `docs/tasks/T025-respaldo-en-la-nube.md` y `docs/meetings/T025-refinamiento/`.

## Alcance

### Incluye

- Punto de restauracion en `ArranqueProceso` tras `SingleInstanceCoordinator` y antes de T019, SQLite y worker (D13); matriz con T019.
- Detencion ordenada del executor; mtime preservado; lectura cancelable de archivos no descargados.
- ADR "Restauracion transaccional al arranque" (D15).

### No incluye

- Fusion de datos; restaurar la e.firma.

## Dependencias

- T025.1, T025.2

## Criterios de aceptacion

- [x] [T025.2/T025.5] Ida y vuelta: base sintetica (XAXX010101000) y 3 ZIP se respaldan y restauran con SHA-256 identicos e `integrity_check` = ok; una base sin perfiles ni paquetes tambien.
- [x] Un esquema mas nuevo se rechaza antes de tocar nada; uno anterior se migra a la version actual; tras restaurar, las credenciales quedan vacias, los perfiles muestran "requiere registrar e.firma" y no se hacen llamadas SAT hasta registrarla.
- [x] Restaurar con una operacion SAT activa rechaza nuevas operaciones, solicita la cancelacion, espera el cierre, no aplica resultados posteriores y reinicia.
- [x] Restaurar con otro HOME resuelve los paquetes bajo la nueva raiz y conserva su mtime (sin reindexar); un corte en cualquier fase queda recuperable al siguiente arranque sin estado mixto; `pre-restauracion-<fecha>` queda intacta y no choca con una existente; la migracion T019 no elige la carpeta equivocada; el archivo se vuelve a verificar si cambia entre verificacion y sustitucion.
- [x] Leer un respaldo aun no descargado por el proveedor (simulado con un lector lento o bloqueante) no congela la UI y se puede cancelar.
- [x] [T025.1/T025.5/T025.6] ADRs nuevos registrados; README y requirements actualizados.
- [x] Build `-Werror`, `ctest` y `git diff --check` pasan; pruebas con `QTemporaryDir` y datos sinteticos.

## Verificacion

`ctest`; las comprobaciones manuales indicadas en los criterios las hace el usuario en el bundle firmado.

## Resultado

- `RestauracionService`: autentica con la KEK de contrasena o de recuperacion, lee en un hilo cancelable (archivos aun no descargados), extrae a stagings privados en el volumen de cada destino, valida metadatos, esquema (`sqlite_master` contra las migraciones) y rutas, migra esquemas anteriores, borra la e.firma, fija mtime y devuelve fecha e id autenticados.
- Marcador durable con diario de fases idempotente (`RENAME_EXCL`), validado en cada fase; aplicacion en `ArranqueProceso` tras la instancia unica y antes de T019, SQLite y worker; `pre-restauracion-<UTC>` sin choques ni adopcion de carpetas ajenas; reverificacion al retomar; reversion recuperable; seccion `respaldo`, id de instalacion y `respaldo/` conservados.
- Detencion ordenada y relanzamiento (auxiliar que espera el fin del proceso; no se relanza con App Translocation); `_exit` si queda un hilo de lectura colgado.
- D22: la reconciliacion de e.firma se omite mientras haya datos previos propios o el registro no se pueda leer; `descartarDatosPrevios()`.
- Exclusion de Time Machine en stagings y `pre-restauracion`; staging `.noindex`; espacio libre comprobado.
- ADR 0022, RF-020 en requirements y README.
- Verificacion: build `-Werror`, `ctest -j8` 33/33, 57 casos de restauracion, 9 de relanzamiento, `git diff --check`; seguridad y macOS aptos, calidad aprobada en la tercera revision.
- Pendiente manual (T025.6): restauracion real con relanzamiento, File Provider, volumenes distintos, corte de energia en una Mac de prueba.
